# Подзадачи MVP

Разбивка [rfc-mvp.md](rfc-mvp.md) на выполнимые куски. Порядок внутри блока — по зависимостям; задачи без общих зависимостей делаются в любом порядке.

Оценки: **S** — до половины дня, **M** — день-два, **L** — больше двух дней.
«Готово, когда» — то, что можно проверить, а не ощущение завершённости.

Сводка: 8 задач в этапе 0, 18 в точке 1, 10 в точке 2.

### Результаты этапа 0 (T0.2–T0.5)

**Ворота пройдены с запасом.** Челлендж решился сам при первом же заходе: HTTP 200, кука `cf_clearance` получена, ручных вмешательств — **ноль** при пороге «не более одного на 5 глав». Профиль пережил и перезапуск браузера, и перезагрузку ВМ. Лестница отступления из §6 концепции не понадобилась.

| Проверка | Итог |
|---|---|
| Первый заход, headful + постоянный профиль | 200, челленджа нет |
| Перезапуск процесса браузера, тот же профиль | 200, челленджа нет |
| Перезагрузка ВМ, профиль с диска | 200, челленджа нет; сервисы поднялись сами |
| **Headless на том же профиле** | **403, челлендж — при живой `cf_clearance`** |

**Headless не работает — это решение, а не наблюдение.** Куки недостаточно: Cloudflare распознаёт headless и отдаёт 403 даже с валидной `cf_clearance` в профиле. Значит Xvfb и headful — постоянный режим работы загрузчика, а не костыль для первого захода. Прямо влияет на T1.3 и на состав ВМ.

**Сайт: 无忧书城.** Схема URL — `/{жанр}/{книга}/{номер}.html`, книга-образец `renwen/zhuguniangjintiandiaokenglemei` (550 глав). Пагинации внутри главы нет — **T1.5 (склейка страниц) в MVP может не понадобиться**, но проверить на второй книге стоит. Ссылок на `.txt` не нашлось: качаем поглавно. Иероглифы упрощённые — 145 маркеров против 0 традиционных, канон B5 подтверждён.

| Замер | Значение |
|---|---|
| Видимый текст главы | **3157 иероглифов** (было предположение 5000) |
| Весь текст из HTML | 5424 иероглифа |
| Абзацев `<p>` | 76 |
| Предложений по терминаторам | ~153, медиана 19 символов |
| Предложений короче 8 символов | 25, то есть 16% |
| Батчей перевода по 10 000 символов | **1** |

Два вывода из замеров. Первый: **около 40% текста в HTML — навигация и списки глав**, поэтому generic-извлечение переводило бы мусор и увеличило счёт примерно в полтора раза — адаптер T1.4 окупается сразу. Второй: правило «склеивать куски короче 8 символов» из RFC §5.2 задевает каждое шестое предложение — то есть оно не косметика, и его надо проверять на снапшотах.

Цифры по предложениям сняты грубым разбором HTML, до нормализации и адаптера: там есть выброс в 5049 символов — это склеенная навигация, а не предложение. Точные значения появятся после T1.4 и T1.7.

### Результаты T0.6 — переводчик

Сервисный аккаунт `chinese-reader-translate` (`ajem2oicvd3rusvbit1m`), роль `ai.translate.user` на каталог, API-ключ лежит в `/etc/chinese-reader/env` с правами `600 root:root`. Биллинг через CLI не виден (нужна роль `billing.accounts.viewer`), но раз ВМ создалась и переводы проходят — платёжный аккаунт активен.

| Проверка | Итог |
|---|---|
| Перевод 3 предложений | 0,45 с |
| Батч из 60 предложений | принят целиком, ответ в том же порядке |
| Имя собственное `江雪明` | транслитерировано верно **без глоссария** |
| 离合词 `帮忙` в разорванной форме | разобран верно |
| Чэнъюй `一见如故` | **переведён неверно** — буквально, мимо смысла |
| Глоссарий `zh→ru` | **поддерживается** |

Два вывода. Первый: **чэнъюй — подтверждённое слабое место**, ровно как предсказывали документы; имена и сепаратные глаголы движок держит сам, так что глоссарий нужен точечно, а не на весь словарь. Второй, важный для этапа 1: на терминах, которые движок и так переводит правильно, **глоссарий задваивает результат** — подстановка добавляется к уже переведённому. Значит в глоссарий главы должны попадать только слова с заведомо неверным дефолтным переводом, а не все слова пользователя. Это меняет формулировку T1 этапа 1: нужен не «собрать глоссарий из личного словаря», а «собрать из тех слов, где пользователь исправил перевод».

### Результаты T0.7 — дамп БКРС

Ежедневная выгрузка одним файлом: `bkrs.info/downloads/daily/dabkrs_<ГГММДД>.gz`, **83,4 МБ** в архиве, формат **DSL**, кодировка UTF-8, направление `Chinese → Russian` объявлено в шапке.

Структура плоская: строка-заголовок без отступа, строки перевода с отступом, в среднем 2 строки на статью. Разметка — закрытый набор тегов: `[m1]`/`[m2]` (уровни списка), `[p]` (пиньинь и пометы), `[ex]` и `[*]` (примеры), `[c]`, `[i]` (оформление). Фикстура на 30 статей — `data/bkrs-sample.dsl`.

**Оценка T2.2 снижена с M–L до M.** Опасение было про «DSL с вложенной разметкой на несколько дней»; по факту вложенности нет, теги перечислимы, а `[ex]`/`[*]` мы всё равно выкидываем на выдаче. Это парсер построчного формата со стриппером тегов. Фолбэк на CC-CEDICT остаётся в запасе, но по текущим данным не понадобится.

**Что делать при провале T0.8.** Ступень 2 — выпускать трафик ВМ через домашний адрес (WireGuard или прокси на домашнем роутере), весь сервис остаётся на ВМ. Ступень 3 — гибрид: загрузчик на ноутбуке отдаёт текст в API. Ступень 4 — расширение для браузера. Ступени 3 и 4 меняют только T1.3 и схему развёртывания; всё остальное в плане остаётся как есть.

### Созданная инфраструктура (T0.1)

| Что | Значение |
|---|---|
| Каталог | `default`, `b1g5qs4tjoe3s8v23g0f` (облако `cloud-seleznevn`) |
| ВМ | `chinese-reader`, `fhmvj6lggvte3tmjechg`, `ru-central1-a`, `standard-v3`, 2 vCPU 100% / 4 ГБ |
| Диск | `chinese-reader-boot`, `network-ssd`, 20 ГБ, образ `ubuntu-2404-lts-oslogin-v20260803` |
| Сеть | `lenta-net` / `lenta-subnet-a` (`e9b1fdko7aik7vs0bobo`), внутренний адрес `10.130.0.11` |
| Группа безопасности | `chinese-reader-sg`, `enpcuq147t65944mpcmi`: ingress 443/tcp и 22/tcp с `0.0.0.0/0`, egress любой |
| Вход | `yc-user`, ключ `id_ed25519`, парольная аутентификация отключена образом |

Публичный IPv4 здесь намеренно не записан: он эфемерный и меняется при пересоздании, а репозиторий — не место для адреса машины с открытым SSH. Актуальный адрес — `yc compute instance get --name chinese-reader`.

Два отступления от исходной формулировки задачи, сделанные осознанно:

- **Порт 22 открыт всем, а не «с домашнего адреса».** Текущий внешний адрес рабочей машины — IPv6 из корпоративной сети, в подсети ВМ IPv6 нет вовсе, а домашний адрес динамический. Привязка к адресу дала бы иллюзию защиты и реальный риск потерять доступ. Защита — ключевая аутентификация; парольный вход в образе отключён.
- **Заведена отдельная группа безопасности.** Дефолтная в этой сети разрешает вход с `0.0.0.0/0` по любому протоколу, и три соседние ВМ работают именно с ней. Наша ВМ — единственная в каталоге с ограниченным набором портов.

**T0.5 и T0.7 определяют оценку остального.** Если глава окажется вдвое больше — вырастет число батчей и цена; если дамп БКРС окажется в DSL с вложенной разметкой — T2.2 превращается из M в L.

## Что можно делать параллельно

- **T0.6** (Yandex Cloud, переводчик) и **T0.7** (БКРС) не зависят от челленджа — делаются, пока идёт возня с T0.3.
- **T1.1–T1.2** (каркас, миграции) не зависят от этапа 0 вообще.
- **T2.1–T2.4** (словари) не зависят от точки 1 — можно готовить, пока делается рендер.
- **T1.15** (рендер) — самая тяжёлая задача точки 1; начинать её стоит на моковых данных, не дожидаясь T1.12.

## Порядок, если времени мало

Минимальная цепочка до первой пользы: T0.1 → T0.2 → T0.3 → T1.1 → T1.2 → T1.3 → T1.4 → T1.6 → T1.7 → T1.8 → T1.13 → T1.15. На этом месте глава уже читается локально с сегментацией — без перевода, API и развёртывания. Дальше по приоритету: перевод (T1.9, T1.16), словарь (T2.1, T2.4, T2.5), развёртывание (T1.17, T1.18).
