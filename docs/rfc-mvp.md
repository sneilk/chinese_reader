# RFC: MVP — чтение одной главы китайской новеллы с карточками и словарём

Статус: черновик к реализации.
Дата: 2026-08-06.
Основание: решения A/B/C/D и M1–M2 из [concept-review.md](concept-review.md) §0.1. Здесь они не пересказываются — только то, что из них следует для кода.
Читатель: тот, кто это будет писать (он же автор).

## 1. Что делает MVP

Одна глава китайской веб-новеллы, открытая по прямой ссылке, читается в собственном ридере: слова кликабельны, значения приходят из локальных словарей, перевод предложения уже готов к моменту открытия, сохранённые слова попадают в личный словарь вместе с контекстом.

Полный сценарий:

```
вставил URL главы
  → сервис грузит её реальным браузером, извлекает текст, режет на предложения и токены,
    переводит все предложения одним-двумя запросами и складывает в SQLite
  → читаю
  → удержание на иероглифе → подсказка у пальца: слово, чтение, значение
  → двойной тап → карточка: пиньинь, значения, перевод предложения
  → правлю границы, если сегментатор ошибся
  → «в словарь» → слово с контекстом-предложением сохранено
  → открываю экран словаря и вижу, что накопилось
```

### Входит

| # | Требование |
|---|---|
| R1 | Загрузка главы по URL через Playwright с persistent-профилем; классификация отказов |
| R2 | Извлечение текста адаптером `51shucheng` + generic-фолбэк; склейка пагинированной главы |
| R3 | Нормализация текста, резка на предложения, сегментация jieba со словарём приложения |
| R4 | Перевод всех предложений главы через Яндекс.Переводчик, батчами ≤10 000 символов |
| R5 | Импорт БКРС и CC-CEDICT в SQLite + FTS5 |
| R6 | Ридер: рендер по токенам, тап / удержание / двойной тап / drag, подсказка у пальца и панель карточки снизу |
| R7 | Карточка: пиньинь, значения, перевод предложения, свои поля (перевод и заметка) |
| R8 | Сохранение слова в личный словарь вместе с контекстом-предложением |
| R9 | Экран личного словаря: список, правка своих полей, удаление |
| R10 | Развёртывание в Yandex Cloud: ВМ, HTTPS, basic auth, бэкап в Object Storage |

### Не входит — осознанно

Оглавление и «следующая глава»; библиотека и позиция чтения; английский режим; глоссарий переводчика; подсветка по знанию и статусы слов; контекстный разбор (нет LLM-провайдера, [translation.md](translation.md) §1); оффлайн и PWA; SRS, статистика, аудио; **ручная вставка текста главы при отказе загрузчика** — вместо неё внятная причина и повтор.

### Допущение, которое проверено (T0.3–T0.5)

Прежняя редакция строилась на догадках о содержимом `51shucheng.net` — сайт был целиком за челленджем. Теперь замерено на живой главе: **3157 иероглифов** видимого текста, 76 абзацев, ~153 предложения, упрощённые иероглифы, пагинации внутри главы нет. Глава укладывается **в один батч перевода** и стоит около **1,6 ₽** вместо предполагавшихся 2,5 ₽.

Одна поправка к плану: около 40% текста в HTML — навигация и списки глав. Generic-извлечение переводило бы этот мусор, увеличивая счёт примерно в полтора раза, так что адаптер (R2) окупается с первой же главы, а не «когда-нибудь».

## 2. Критерии приёмки

MVP закрыт, когда **на телефоне**, по HTTPS, после ввода пароля:

1. Глава открывается по URL и дочитывается целиком за один заход.
2. Тап по любому иероглифу даёт карточку; перевод предложения появляется без задержки и без сети к внешнему API.
3. Границы выделения правятся руками, исправленное слово сохраняется и попадает в userdict сегментатора.
4. Накоплено **≥30 слов** с непустым контекстом-предложением.
5. Экран словаря показывает их и позволяет поправить свой перевод и удалить ошибочную запись.
6. **Ни одной ручной правки в SQLite** за всё время прогона.
7. Отказ загрузчика отличим по причине: челлендж / 404 / пустое извлечение.

Явное ограничение MVP, которое в приёмку не входит: нужна живая связь с сервером, оффлайна нет.

## 3. Архитектура

```
браузер (React)
   │  HTTPS + basic auth
   ▼
Caddy ──► FastAPI (uvicorn, systemd)
              ├── fetchers/   BrowserFetcher (Playwright, persistent profile)
              ├── adapters/   51shucheng | generic
              ├── lang/       нормализация · предложения · jieba · пиньинь
              ├── providers/  YandexTranslate
              └── db/         SQLite + FTS5
```

Всё на одной ВМ. Единственный внешний вызов во время работы — Яндекс.Переводчик, и только в момент загрузки главы.

Интерфейсы, которые обязаны существовать с первого дня, потому что за ними стоят принятые решения:

```python
class Fetcher(Protocol):
    async def get(self, url: str) -> FetchResult: ...      # html | FetchError

class SiteAdapter(Protocol):
    def matches(self, url: str) -> bool: ...
    async def chapter(self, url: str) -> ChapterRaw: ...   # title, paragraphs[], next_url|None

class Translator(Protocol):
    async def translate(self, texts: list[str], src: str, dst: str,
                        glossary: list[tuple[str, str]] | None = None) -> list[str]: ...
```

`Translator` пакетный по сигнатуре — это не преждевременное обобщение, а прямое следствие того, что глава переводится целиком, и заранее оставленное место под будущий одиночный контекстный разбор ([concept-review.md](concept-review.md) §4.2).

## 4. Конвейер загрузки главы

Загрузка асинхронная: HTTP-запрос возвращается сразу, клиент опрашивает статус. Синхронный вариант отпадает — Playwright плюс перевод легко перешагнут таймаут прокси.

```
POST /api/chapters {url}
   → создаём запись, status=fetching, отдаём 202
   → фоновая задача:
        BrowserFetcher.get(url)         ошибка → failed + error_kind
        adapter.chapter(html)           пусто  → failed + error_kind=empty_extract
        нормализация → предложения → jieba
        status=segmented                ← ГЛАВА УЖЕ ЧИТАЕМА
        перевод батчами                 ошибка → status=segmented, error_kind=translate_failed
        status=ready
```

| status | Что значит | Читается? |
|---|---|---|
| `fetching` | идёт загрузка и разбор | нет |
| `segmented` | текст и токены есть, переводов нет или не все | **да** |
| `translating` | идёт перевод | да |
| `ready` | всё на месте | да |
| `failed` | текст получить не удалось | нет |

`error_kind`: `challenge`, `not_found`, `empty_extract`, `fetch_timeout`, `adapter_error`, `translate_failed`, `budget_exceeded`. Первые пять означают `failed`, последние два — глава остаётся на `segmented` и читается без переводов (решение по вопросу 6). Повторный перевод — отдельной кнопкой, уже переведённые предложения не переотправляются.

`budget_exceeded` отделён от `translate_failed` намеренно: это не сбой на той стороне, а наш потолок расходов, и лечится он не повтором, а решением потратить больше. Показывать их одинаково значило бы предлагать читателю жать «попробовать снова» до посинения.

**Повторный `POST` с тем же URL** не ходит в сеть: `chapters.url` уникален, возвращается существующая запись. Это то самое «за одной главой ходим один раз» из §1.3 концепции.

**Пагинация.** Если адаптер вернул `next_url` в пределах той же главы — страницы склеиваются в одну запись `chapters` с задержкой между запросами. Жёсткий потолок — 20 страниц; при превышении `failed` + `adapter_error`, а не молчаливая обрезка. Склейка происходит **до** нормализации и сегментации, иначе офсеты и границы предложений разъедутся.

### Параметры загрузчика

Таблица дефолтов в конфиге, каждый переопределяется через env; калибруется по первому прогону.

| Параметр | Дефолт |
|---|---|
| режим | **headful под Xvfb — обязательно.** Headless на том же профиле с живой `cf_clearance` получает 403 (проверено в T0.3) |

## 5. Языковой слой

### 5.1. Нормализация и канон

Каноном главы становится **нормализованный текст**; сырой HTML не хранится. Офсеты токенов и границы предложений считаются по канону ([segmentation.md](segmentation.md) §1).

Нормализация: убрать zero-width и неразрывные пробелы, схлопнуть повторяющиеся пробелы, снять отступы из идеографических пробелов, оставить абзацы. **Полноширинная пунктуация сохраняется** — она несёт границы предложений и нормально смотрится в тексте (отсюда NFC, а не NFKC: последний схлопнул бы её в ASCII).

Пункт «привести кавычки к одному виду» из первой редакции **отменён**. Переписывание пунктуации — изменение чужого текста, которое читатель увидит в ридере, а цель у правила была служебная: чтобы резчик предложений не спотыкался о разные кодовые точки визуально одинаковых кавычек. То же достигается тем, что резчик знает **набор** закрывающих кавычек, и текст остаётся нетронутым.

### 5.2. Резка на предложения

Единица перевода, поэтому правила фиксируются, а не подбираются по ходу:

- терминаторы: `。`, `！`, `？`, `!`, `?`, `……`, а также перевод строки;
- закрывающие кавычки и скобки (`」`, `』`, `"`, `）`) прилипают к предыдущему предложению;
- `；` и `，` не режут;
- кусок короче 8 символов склеивается со следующим — иначе реплики диалога рассыпаются на огрызки и переводятся мусором. **Склейка идёт только внутри абзаца:** абзац в китайской новелле — это чаще всего реплика, и склеить короткую реплику со следующей значило бы отдать переводчику диалог двух персонажей как одну фразу. Короткий абзац остаётся отдельным предложением — это законная единица перевода, а не огрызок;
- предложение хранит `start`/`end` в каноне, поэтому карточка вырезает контекст по офсетам, а не по копии строки.

### 5.3. Сегментация

По [segmentation.md](segmentation.md) §9: jieba, словарь приложения в userdict, токены с офсетами в `tokens_json`, слова пользователя с высокой частотой. Не входит: pkuseg, `segmentation_overrides` по главам, частотные списки, 离合词.

### 5.4. Словари

- **БКРС** — импортируется целиком, однократным скриптом. Фильтрация (иероглифический заголовок ≤4 знаков, без примеров) применяется **на выдаче** в карточку и при сборке userdict, а не при импорте: переимпорт дорог, фильтр на выдаче бесплатен.
- **CC-CEDICT** — источник пиньиня и подстраховка; он же кормит сегментатор.
- Если формат дампа БКРС окажется неподъёмным (решение по вопросу 7) — MVP выходит на CC-CEDICT, карточка временно zh→en, БКРС переезжает на следующий этап. Развилка принимается по факту, а не заранее.

### 5.5. Карточка, когда статьи нет

Типовой случай — имя героя. Показываем: `pypinyin` **с явной пометкой «авто»**, значения отдельных иероглифов, перевод предложения сверху, свои поля для заполнения вручную. Это сознательное отступление от §2.3 концепции («пиньинь из словарной статьи»), ограниченное случаем «статьи нет вообще».

## 6. Перевод

По [translation.md](translation.md). Существенное для кода:

- батч — массив `texts[]`, суммарно **≤10 000 символов**; ответ в том же порядке, раскладывается по `sentences.idx`;
- глава в ~5000 иероглифов укладывается в один-два запроса;
- `sentences.translation` nullable — глава живёт и без переводов;
- считаем и пишем `chars_sent` на каждый запрос; мягкий потолок на главу и на месяц в конфиге, при превышении — отказ с внятным сообщением, а не тихий счёт. Месячный расход считается по журналу `translation_usage` (строка на запрос): в `chapters.chars_sent` лежит накопительный итог главы без даты, а тарификация идёт за календарный месяц. Ноль в конфиге означает «не ограничивать»;
- глоссарий в MVP не используется, но `glossary_hash` в схеме есть с самого начала: без него после появления глоссария старые переводы молча не обновятся.

## 7. Схема данных

SQLAlchemy 2.0 + Alembic; FTS5 создаётся через `op.execute`. Схема заведомо поедет (глоссарий, статусы слов, SRS), поэтому миграции с первого коммита.

```sql
sources(id, kind, site, base_url, title, author, lang, created_at)

documents(id, source_id → sources, title, lang, created_at, updated_at)

chapters(id, document_id → documents, idx, title,
         url TEXT UNIQUE NOT NULL,
         content TEXT,                    -- канон
         tokens_json TEXT,                -- [[start, end, kind], ...]
         status TEXT NOT NULL,            -- fetching|segmented|translating|ready|failed
         error_kind TEXT, error_detail TEXT,
         chars_sent INTEGER DEFAULT 0,
         fetched_at, created_at, updated_at)

sentences(id, chapter_id → chapters, idx, start, end,
          translation TEXT, glossary_hash TEXT, translated_at,
          UNIQUE(chapter_id, idx))

dict_entries(id, lang, headword, traditional, reading, pos,
             senses_json, source, freq)
dict_fts                                   -- FTS5 по headword

user_words(id, lang, headword, reading,
           user_translation TEXT, note TEXT,          -- M2
           status TEXT DEFAULT 'new',                 -- задел, в UI не используется
           added_at, updated_at, due_at, ease,        -- задел под SRS
           UNIQUE(lang, headword))

contexts(id, user_word_id → user_words, chapter_id → chapters,
         sentence_id → sentences, sentence TEXT,
         offset_start, offset_end, created_at)

word_occurrences(headword, chapter_id → chapters, count,
                 PRIMARY KEY(headword, chapter_id))

lookups(id, provider, direction, glossary_hash, key_hash,
        response_json, chars_sent, created_at,
        UNIQUE(provider, direction, glossary_hash, key_hash))

settings(key PRIMARY KEY, value)
```

`contexts.sentence` дублирует текст предложения намеренно: карточка должна пережить удаление главы.

## 8. API

Один префикс `/api`, JSON, ошибки в виде `{"error": {"kind": ..., "message": ...}}`.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/chapters` | `{url}` → `202 {id, status}`; идемпотентен по URL |
| `GET` | `/api/chapters/{id}` | статус и, начиная с `segmented`, весь контент главы одним ответом |
| `POST` | `/api/chapters/{id}/translate` | дозалить перевод после отказа |
| `GET` | `/api/lookup?word=&lang=zh` | значения из локальных словарей |
| `POST` | `/api/words` | сохранить слово с контекстом |
| `GET` | `/api/words` | личный словарь, страницами |
| `PATCH` | `/api/words/{id}` | свой перевод и заметка |
| `DELETE` | `/api/words/{id}` | удалить ошибочную запись |

`GET /api/chapters/{id}` отдаёт главу целиком — текст, токены, предложения с переводами. Для главы в 5000 иероглифов это сотни килобайт, что для одного пользователя нормально и избавляет от отдельных запросов на каждое предложение.

```json
{
  "id": 1, "title": "第一章", "status": "ready", "error": null,
  "content": "…канон…",
  "tokens": [[0, 2, "word"], [2, 3, "punct"]],
  "sentences": [{"idx": 0, "start": 0, "end": 12, "translation": "…"}]
}
```

## 9. Клиент

React + TypeScript + Vite. Состояние — `useState` и тонкий `api.ts`; ни Redux, ни react-query в MVP не нужны — экранов три.

| Экран | Содержимое |
|---|---|
| Ввод | поле URL, кнопка, прогресс по статусу главы |
| Чтение | текст главы, панель карточки снизу |
| Словарь | список слов: слово, пиньинь, значение, контекст, дата; правка своих полей, удаление |

**Рендер главы — единственное место, где легко потерять день.** Глава даёт ~3000 span-ов. Не делать компонент на токен и не вешать обработчик на каждый: один контейнер, один обработчик, делегирование по `data-s` / `data-e` ([segmentation.md](segmentation.md) §4). Жесты: тап — подсветка слова, удержание — подсказка у пальца, двойной тап — панель, drag — расширение в пределах предложения. Ответ соразмерен жесту: панель на треть экрана стоит второго касания, а не первого.

Вёрстка адаптивная, приёмка на телефоне (§2), десктоп получается тем же layout-ом.

## 10. Развёртывание: Yandex Cloud

| Ресурс | Значение |
|---|---|
| ВМ | Compute Cloud, Ubuntu 24.04 LTS, 2 vCPU (100% доля), 4 ГБ RAM, SSD ≥20 ГБ, публичный IP |
| Порты | 443 и 22 отовсюду, вход по SSH только по ключу (парольный отключён образом); больше ничего наружу. Отдельная группа безопасности, а не дефолтная — та в этой сети открыта полностью |
| DNS | домен + A-запись на публичный IP |
| TLS и вход | Caddy: автоматический Let's Encrypt + **basic auth** (решение по вопросу 10) |
| Процессы | systemd: `chinese-reader-api.service`; без Docker |
| Секреты | `EnvironmentFile=/etc/chinese-reader/env`, права `0600`; в git не попадает ничего |
| Переводчик | сервисный аккаунт в том же каталоге, роль на использование Translate, API-ключ в env |
| Бэкап | ночной таймер: `sqlite3 .backup` → `rclone` в Object Storage; отдельный сервисный аккаунт с доступом ровно к одному бакету |
| Логи | journald, ротация по умолчанию |
| Данные | `/opt/chinese-reader/data` — SQLite, словарные дампы, профиль браузера; выкладкой не затирается |

**Ручной проход челленджа**, если понадобится: `x11vnc` к тому же Xvfb, **только через SSH-туннель**, порт наружу не открывается.

**Цикл разработки:** пишем и гоняем тесты локально, но проверку загрузчика делаем на ВМ с самого начала — именно её адрес определяет главный риск, и локальный успех о нём ничего не говорит.

Точные имена ролей сервисных аккаунтов и квоты каталога сверяются в консоли на шаге разведки (§13), а не берутся из этого документа на веру.

## 11. Порядок работ

Две демонстрируемые точки — так объём остаётся управляемым при любом темпе (по п. 12 число часов не названо, поэтому берётся вариант, работающий в обоих случаях).

**Этап 0 — ворота.** Поднять ВМ, Playwright с persistent-профилем, открыть главу `51shucheng`. Померить: проходит ли челлендж, переживают ли куки перезапуск браузера и ВМ, сколько ручных вмешательств потребовалось. Порог — не более одного вмешательства на 5 глав за 2 дня (решение по вопросу 5); хуже — следующая ступень лестницы §6 концепции. Здесь же снимается HTML-фикстура и замеряется реальный размер главы.

**Точка 1 — «глава грузится и читается».** R1–R6 без карточки: конвейер, статусы, нормализация, предложения, сегментация, перевод, рендер с подсветкой границ токенов. Проверяется тем, что глава читается на телефоне и перевод предложения показывается по тапу.

**Точка 2 — «карточка и словарь».** R7–R9: словари в базе, карточка, правка границ, сохранение с контекстом, экран словаря. Плюс R10 в законченном виде: бэкап, потолок расходов, диагностика отказов.

Внутри каждой точки порядок диктуется зависимостями: сначала конвейер и схема, потом API, потом клиент.

## 12. Тесты

- **Адаптер** — на сохранённых HTML-фикстурах, без сети. Ломаться должен разбор, а не соединение.
- **Резка на предложения и сегментация** — регресс-снапшоты: 20–30 предложений реальной главы с зафиксированным выводом. Эталонная разметка границ, если понадобится точность, берётся из открытого корпуса, а не размечается вручную.
- **Перевод** — записанные ответы провайдера; тесты не тратят символы.
- **Импортёр словаря** — 20–30 реальных статей БКРС как фикстура.
- **API** — happy path каждого эндпоинта плюс все `error_kind`.
- Клиентские тесты в MVP не пишем: три экрана, приёмка ручная.

`ruff` и `pytest`, pre-commit. Python 3.12.

## 14. Риски

| Риск | Реакция |
|---|---|
| Челлендж не проходится с ВМ | Лестница §6 концепции; ступень «профиль с ноутбука» из неё удалена как неработающая (`cf_clearance` привязан к IP и UA) |
| БКРС в неподъёмном формате | MVP на CC-CEDICT, карточка временно zh→en |
| Машинный перевод плох на этом тексте | Взять текст попроще; глоссарий (следующий этап) — главный рычаг |
| Адаптер ломается при смене вёрстки | Фикстуры + generic-фолбэк + внятная диагностика вместо пустой главы |
| Расходы вышли из-под контроля | Потолок в конфиге и `chars_sent` в каждой записи |
| Скоуп растёт | Список «не входит» в §1 — граница; всё оттуда переезжает на следующие этапы целиком, а не по кусочку |

## 15. Что осознанно осталось нерешённым

- **Контекстный разбор** — половина решения B2. Нет LLM-провайдера; интерфейс `providers/` к нему готов, добавление стоит один файл ([translation.md](translation.md) §1).
- **Оффлайн** — требует PWA; в MVP нужна живая связь с сервером.
- **Глоссарий** — следующий этап, но `glossary_hash` в схеме уже есть.
- **Статусы слов, подсветка, SRS, статистика, аудио** — поля `status`, `due_at`, `ease` заведены, UI нет.
- **Темп работ** — число часов в неделю не названо; поэтому план разбит на две самостоятельные точки вместо одного длинного этапа.
