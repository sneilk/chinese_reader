## 0. Как я понял идею

Три блока, которые в исходной формулировке звучат как три разных продукта:

1. **Скрапер** — обёртка над внешними сайтами, выгрузка их контента в PDF.
2. **Словарь** — накопительная база en→ru и zh→ru, наполняемая через походы во внешние API.
3. **Ридер** — чтение текста с возможностью выделить слово/фразу и получить перевод, который тут же оседает в словаре.

Связного продукта из них получается ровно один, если считать скрапер **источником контента для ридера**, а словарь — **побочным продуктом чтения**. Пользовательский цикл тогда такой:

```
открыл главу на сайте → она отрисовалась в моём ридере → читаю
   → ткнул в незнакомое слово → значение из локального словаря
   → не понял предложение → перевод (уже переведён при загрузке главы)
   → слово с контекстом-предложением упало в личный словарь
   → словарь красит текст и кормит глоссарий переводчика
   → повторения по знакомым словам
```

Это фактически LingQ / Readlang / Pleco Reader, собранный под себя. Ниша живая, а самодельная версия выигрывает за счёт русского языка (в существующих продуктах zh→ru почти нет) и отсутствия подписки.

**Главный вопрос концепции закрыт (A1):** обёртка идёт первой. Приложение начинается не с импорта файлов, а с «дай URL главы — читай её в моём ридере». Свой ридер поверх `.txt`/`.epub` остаётся в плане, но позже.

Важно, что этот выбор **ничего не выбрасывает**. Обёртка и собственный ридер отличаются ровно одним слоем — источником текста:

```
живой сайт  ─┐
             ├─→ нормализация → сегментация → рендер → карточка → личный словарь
файл .epub  ─┘        (общее для обоих: ~80% работы)
```

То есть A1 меняет порядок работ, а не архитектуру. Цена решения другая и она реальная: MVP становится дороже, потому что втягивает в себя браузерный загрузчик и адаптеры сайтов, которые прошлая редакция §5 откладывала на четвёртый этап. См. §5.

## 1. Предложения по скраперу

### 1.1. PDF — плохой промежуточный формат, теперь и необязательный конечный

*Решение A6: PDF не требование. Канон — структурированный текст, экспорт — EPUB/Markdown.*

PDF — формат фиксированной вёрстки. Если сохранять контент в PDF, то для ридера его придётся **парсить обратно**, теряя абзацы, порядок текста, разбиение на главы, и получая мусор из колонок и переносов. Особенно больно с CJK: в PDF китайский текст часто лежит поглифно, без границ слов и иногда без пробелов между блоками.

Итоговая схема:

- **Каноническое хранение:** очищенный текст с абзацами + метаданные (заголовок, автор, URL, номер главы) — это то, что читает ридер и по чему строится токенизация.
- **Экспорт:** Markdown (тривиально) и EPUB (`ebooklib`) — по требованию, из канонического формата.
- **PDF:** выпадает из плана. Если когда-нибудь понадобится — генерируется тем же экспортом через WeasyPrint, и тогда нужен шрифт с китайскими глифами (Noto Sans/Serif CJK SC), иначе на выходе квадраты.

### 1.2. Стек извлечения — реальный браузер обязателен

Прошлая редакция предполагала «Playwright только там, где без него никак». Проверка обоих названных сайтов (полностью — [sources.md](sources.md)) показала, что «никак» — это оба:

| Сайт | Что мешает | Вывод |
|---|---|---|
| `51shucheng.net` | Cloudflare-челлендж на весь сайт, включая `sitemap.xml`: `curl` получает 403 «Just a moment…» | только реальный браузер |
| `novelarrow.com` | SSR отдаётся, но список глав грузится клиентским JS через `/api/`, закрытый в robots | только реальный браузер |

Отсюда стек:

- **Загрузчик за интерфейсом:** `Fetcher.get(url) -> html`, реализации `HttpFetcher` (httpx) и `BrowserFetcher` (Playwright, **persistent context** — профиль на диске, чтобы куки Cloudflare пережили перезапуск). Выбор реализации — свойство адаптера сайта.
- **Извлечение контента:** per-site адаптеры `adapters/51shucheng.py` и `adapters/novelarrow.py` с интерфейсом «оглавление → список глав» + «URL главы → заголовок и текст». Generic-фолбэк — `trafilatura`, `readability-lxml` запасным.
- **Кэш скачанного — часть MVP, а не оптимизация:** глава сохраняется в SQLite вместе с токенами и переводами предложений.
- **Диагностика загрузки:** различать «челлендж», «404», «пустое извлечение». Молча отданная пустая глава — худший из отказов, потому что выглядит как баг ридера.

Отдельно и заранее: решение C2 (сервер на ВМ) переносит браузер с домашнего адреса на датацентровый, а это самый спорный для Cloudflare случай. Это главный технический риск проекта — план проверки и отступления в §6.

### 1.3. Вежливость и легальность

*Решения A2, B3 и C2: пользователь один, но приложение живёт на сервере, доступном из сети.*

Формулировка «локальное однопользовательское приложение» после C2 больше не годится буквально. Точнее так: **частный однопользовательский инстанс, закрытый авторизацией и не предназначенный для публичного доступа**. Практические следствия те же, но требуют действий (§4.5), а не только намерений.

- `robots.txt` соблюдаем: у `novelarrow` под запретом `/api/`, `/admin/`, `/login`, `/library`, `/history` — туда не ходим; у `51shucheng` закрыты только служебные каталоги WordPress.
- Задержка между запросами, параллелизм 1, никакого обхода оглавления «про запас» — качаем ту главу, которую читаем. Кэш гарантирует, что за одной главой ходим один раз.
- `novelarrow` объявляет `ai-train=no` и закрывает AI-краулеров. Отправка предложений во внешний переводчик ради собственного чтения — не обучение модели, но границу держим: не собирать корпуса, не публиковать выгрузки, не открывать инстанс наружу.
- Словари: CC-CEDICT требует атрибуции (CC BY-SA) — указать в README. Выгрузка БКРС — на сервере, в git не кладём, наружу не отдаём.
- Инстанс закрыт паролем, помечен `noindex`, ссылка никуда не публикуется. Это не бюрократия, а буквально то, что отличает «читаю себе» от «раздаю чужой контент».

## 2. Предложения по словарю

### 2.1. Не ходить в API на каждое слово

*Решения B1 и C3. Из C3 следует, что слоёв три, и верхнего — контекстного — среди них нет.*

| Слой | Что | Когда срабатывает |
|---|---|---|
| 0. Личный словарь + переводы главы | то, что уже сохраняли или уже переведено при загрузке | мгновенно, бесплатно |
| 1. Локальные словари | БКРС (zh→ru), CC-CEDICT (zh→en + пиньинь), Wiktionary (en→ru) | мгновенно, оффлайн, покрывает ~90% лемм |
| 2. Яндекс.Переводчик | перевод предложений — всей главы разом при её загрузке | один раз на главу, ~2,5 ₽ |
| 3. ~~LLM: контекстный разбор~~ | *провайдера нет — см. §1 в [translation.md](translation.md)* | — |

Ответ B2 («нужны оба варианта») задаёт форму карточки слова — и здесь же виден его недобор:

```
上手                                    ← слово
shàng shǒu                              ← пиньинь (B4)
1. начинать; браться за дело            ← БКРС / CC-CEDICT, локально, мгновенно
2. осваиваться, набивать руку
─────────────────────────────────────
Предложение: 他很快就上手了。
Перевод:     Он быстро освоился.        ← Яндекс, переведено при загрузке главы
─────────────────────────────────────
[ + в словарь ]
    ↑ кнопки «разобрать в контексте» нет: машинный переводчик
      не объясняет, почему здесь именно это значение
```

**Это осознанный недобор по B2, а не упущение.** Для начального уровня (B6) связка «все словарные значения + перевод предложения» закрывает большую часть потребности; «почему именно это значение» становится критично позже. Провайдер спрятан за интерфейсом, так что добавление LLM-слоя позже стоит один файл и ничего не переделывает. Варианты и их цена — [translation.md](translation.md) §1.

Практика работы с переводчиком — API, глоссарий, экономика, кэш — вынесена в **[translation.md](translation.md)**.

### 2.2. Источники данных

Раз zh→ru разрешён (B3), русский словарь становится основным, а английский — дополнением. После C3 его роль ещё выросла: словарь теперь единственный источник **значений** — переводчик даёт только предложения.

- **БКРС** — самый большой zh→ru, основной источник значений. Разобраться с форматом публичной выгрузки и написать однократный импортёр в SQLite.
- **CC-CEDICT** — zh→en, ~120k записей, свободная лицензия (CC BY-SA). Нужен всё равно: он даёт **пиньинь** (B4), подстраховывает там, где в БКРС статьи нет, и им кормится сегментатор ([segmentation.md](segmentation.md) §2).
- **HSK-списки** (HSK 3.0, уровни 1–9) — оценка сложности текста и дефолты под начальный уровень (B6).
- **Wiktionary/Wikidata**, **WordNet** — для английского режима, когда до него дойдёт очередь.

Формат хранения: одна таблица словарных статей в SQLite + FTS5 для поиска. Словари загружаются скриптом при первой настройке сервера, в git не тащатся.

### 2.3. Китайская специфика, которую нельзя игнорировать

- **Сегментация.** В китайском нет пробелов: `我喜欢学习中文` — это 5 слов, а не 7 символов и не 1 слово. Без сегментации фича «выдели слово» не работает вообще. Реализация: **[segmentation.md](segmentation.md)**.
- **Упрощённое ↔ традиционное.** *Решение B5: канон — упрощённые.* Ключ в БД — упрощённое написание, традиционное хранится алиасом. Традиционный текст конвертируется `opencc` **только для сегментации и словарного поиска**, показывается оригинал.
- **Пиньинь и 多音字.** `pypinyin` учитывает контекст, но не идеально: 行 читается `xíng` или `háng`, 长 — `cháng` или `zhǎng`. Пиньинь берём из словарной статьи слова, а не генерируем посимвольно.
- **Единица изучения.** Хранить многоуровнево — отдельные записи для символа, слова и фразы, со связью «входит в состав».
- **Художественная литература (A4)** — самый тяжёлый жанр и для сегментации, и для машинного перевода: вымышленные имена собственные, литературный синтаксис, культивационная терминология. Правка границ пользователем ([segmentation.md](segmentation.md) §4–§5) становится обязательной с первого дня — и после C3 окупается вдвойне: те же слова уходят в глоссарий переводчика ([translation.md](translation.md) §4).
- **Меры счёта, сепаратные глаголы (离合词) типа 帮忙 → 帮了忙, результативные конструкции** — на них ломается и generic-сегментация, и машинный перевод. Для MVP игнорировать, но не удивляться.

Для английского аналог сегментации — **лемматизация**: `running/ran/runs` → `run`, иначе словарь заполнится дублями. `spaCy` или `lemminflect`. Это второй режим, после MVP (A5).

### 2.4. Сохранять контекст, а не только пару «слово — перевод»

Настоятельно: вместе с переводом писать в БД **предложение, в котором слово встретилось**, источник и дату. Без контекста карточка `打 → бить/играть/делать/звонить/…` бесполезна для запоминания. С контекстом она превращается в нормальную карточку и делает возможным экспорт в Anki (`genanki`) — что сильно дешевле, чем писать свой SRS.

После C3 у контекста появилась вторая роль: предложение и его перевод уже лежат в БД после загрузки главы, так что карточка собирается без единого обращения к сети.

## 3. Предложения по ридеру

### 3.1. Выделение текста в китайском

Пользователь не знает, где границы слов — в этом же и смысл приложения. Поэтому «выделить текст мышкой» как единственный способ не годится (подробности — [segmentation.md](segmentation.md) §4):

- Текст **сегментируется один раз, при загрузке главы**, не на лету.
- **Тап/клик по символу** → выделяется весь сегмент-слово, показывается карточка.
- **Drag или тап по соседнему** → выделение расширяется по границам сегментов, до фразы.
- **Долгий тап** → выделение ровно одного символа (когда сегментатор ошибся или хочется разобрать составляющие).

### 3.2. Подсветка по знанию — сильная фича, но не в MVP

Раскраска текста по состоянию слова в личном словаре (`новое / изучается / известно / игнор`) — то, ради чего люди платят LingQ. Эффект: виден прогресс, видна сложность текста до начала чтения, и глаз сам цепляется за нужное.

Почему не в MVP: подсветке нужен накопленный личный словарь. На пустой базе весь текст будет одного цвета «новое», то есть фича не даст ничего, пока не наберётся несколько сотен слов.

Что заложить в MVP, чтобы потом не переделывать: поле `status` в `user_words` (`new | learning | known | ignored`) и агрегат `word_occurrences`. Тогда подсветка добавляется как слой рендера, без миграции данных.

### 3.3. Перевод предложения — центральная фича, и она закрыта

Прямое следствие пары A4 (художественная литература) и B6 (начальный уровень). Китайская веб-новелла при начальном уровне — это 40–60% незнакомых слов на абзац. Пословный перевод такой текст не спасает: даже когда все слова понятны по отдельности, предложение остаётся непонятным.

Хорошая новость от C3: **это ровно то, что машинный переводчик делает хорошо и дёшево**. Более того, посимвольная тарификация делает выгодным перевод всей главы при загрузке (~2,5 ₽, расчёт в [translation.md](translation.md) §3), а значит:

- перевод любого предложения показывается **мгновенно и без сети** — он уже в БД;
- нет задержки в 300–800 мс на каждый запрос;
- единственная точка, где провайдер может отказать, — загрузка главы, где ошибку легко показать внятно;
- та же панель, что и у слова, никаких модалок.

Чего перевод предложения не даёт: понимания, **почему** фраза устроена именно так. Это и есть незакрытая половина B2 (§2.1). Страховка на случай, если новелла окажется неподъёмной, остаётся прежней: режим параллельного текста — оригинал и перевод абзаца рядом. Не в MVP, но в списке, и теперь он дешёвый, потому что перевод уже есть.

### 3.4. Дефолты под начальный уровень и пиньинь

- **Пиньинь в карточке — всегда.** Раз слово незнакомое, его чтение нужно.
- **Пиньинь над текстом (ruby) — переключатель, по умолчанию выключен.** Постоянный пиньинь над иероглифами заметно тормозит обучение чтению: глаз читает латиницу и не запоминает знак. Компромисс на будущее — третье состояние «только для незнакомых», когда появятся статусы слов (§3.2).
- **Ничего не считать «известным» автоматически.** На начальном уровне даже HSK 1 освоен не весь. Импорт HSK-списка как «уже знаю» — отдельная кнопка в настройках.
- **Размер шрифта и межстрочный интервал** — для китайского критичнее, чем для латиницы: мелкий иероглиф просто нечитаем. Крупный дефолт.

### 3.5. Мелочи, которые определяют, будете ли вы этим пользоваться

- Сохранение позиции чтения и мгновенный возврат к ней (при серверной модели — общая для всех устройств, см. C4).
- Ноль модальных окон: перевод — во всплывающей панели снизу, чтение не прерывается.
- Одно нажатие «сохранить в словарь» и одно «я это знаю, больше не подсвечивать».
- Тёмная тема — читать будете вечером.
- **Оффлайн — переоценить.** С сервером на ВМ (C2) «оффлайн» означает PWA с кэшем глав в браузере — отдельная работа, и в MVP её нет. Смягчающее обстоятельство от C3: раз глава переводится целиком при загрузке, ей во время чтения не нужен внешний API — нужен только свой сервер.

## 4. Предложения по архитектуре

### 4.1. Форма приложения — подтверждена (C1)

Решение A1 сузило выбор до «как именно выглядит обёртка», C1 закрепило первый вариант:

| Форма | Что это | Плюсы | Минусы |
|---|---|---|---|
| **Управляемый браузер + свой рендер** ← принято | Playwright с persistent-профилем грузит страницу, адаптер вынимает текст главы, приложение рисует его своим ридером | челлендж проходит браузер; весь UI наш; **этот же рендер нужен будущему своему ридеру** — работа не выбрасывается | Playwright как зависимость (~300 МБ браузера); адаптер на каждый сайт; на ВМ — датацентровый IP (§6) |
| **Расширение для браузера** | content-script поверх живого сайта | сайт как есть: навигация, куки, челлендж — не наша забота; трафик идёт с домашнего адреса | второй кодовый контур (MV3); реактивный DOM Next.js требует MutationObserver; свой ридер потом всё равно писать |
| **HTTP-прокси с переписыванием HTML** | отдаём чужую страницу с инъекцией скрипта | «хожу по сайту как обычно» | CSP, относительные URL, Cloudflare, ломающийся JS. Не брать |

Итог: **FastAPI + Playwright-загрузчик + React-клиент, всё на одной ВМ**. Второй вариант остаётся не альтернативой, а планом отступления, если Cloudflare не пустит браузер с сервера (§6) — и он теперь дешевле, чем был бы с нуля: сервер, БД и словари к тому моменту уже есть.

### 4.2. Раскладка

```
chinese_reader/
  backend/
    app/
      api/          # роутеры FastAPI
      services/     # бизнес-логика: fetch, lookup, translate, export
      providers/    # Яндекс.Переводчик за общим интерфейсом
      fetchers/     # HttpFetcher, BrowserFetcher (Playwright)
      adapters/     # per-site: 51shucheng, novelarrow, generic
      lang/         # сегментация, лемматизация, пиньинь
      db/           # модели, миграции, репозитории
    tests/
  web/              # React + TypeScript (Vite)
  data/             # словарные дампы, профиль браузера, SQLite (не в git)
  deploy/           # конфиг reverse proxy, systemd-юниты (без секретов)
  docs/
```

Ключевое: **`providers/` и `fetchers/` за едиными интерфейсами**. Интерфейс провайдера здесь не абстракция впрок, а конкретная страховка: именно он делает добавление контекстного разбора (незакрытая половина B2) вопросом одного файла, а не переделки.

Форма интерфейса при этом должна учитывать, что провайдеры разные по природе: `translate(texts: list[str], src, dst, glossary) -> list[str]` — пакетный, а будущий разбор — одиночный. Не пытаться свести их к одной сигнатуре.

### 4.3. Данные (набросок)

```
sources        id, kind(web|epub|txt), site, base_url, title, author, lang, created_at
documents      id, source_id, title, lang, toc_json, position, created_at, updated_at
chapters       id, document_id, idx, title, url, content, tokens_json, fetched_at
                                                         -- кэш живых глав лежит здесь же
sentences      id, chapter_id, idx, start, end, translation, glossary_hash, translated_at

dict_entries   id, lang, headword, traditional, reading, pos, senses_json, source(bkrs|cedict)
user_words     id, lang, headword, user_translation, note,
               status(new|learning|known|ignored), added_at, updated_at, due_at, ease
contexts       id, user_word_id, chapter_id, sentence, offset
word_occurrences  headword, chapter_id, count
lookups        id, provider, direction, glossary_hash, key_hash, response_json,
               chars_sent, created_at        -- точечные и повторные запросы + учёт расходов
settings       key, value                    -- пиньинь, тема, размер шрифта
```

Четыре детали:

- `user_translation` и `note` в `user_words` (**M2**) закрывают дыру, которую видно на главном сценарии: карточка собирается из `dict_entries`, а правка границ ([segmentation.md](segmentation.md) §5, склейка `江雪明`) по определению порождает слова, у которых словарной статьи нет. Без своих полей такая карточка сохраняется пустой. Обе колонки nullable и редактируются прямо в карточке.
- `sentences` — новая таблица, прямое следствие C3: раз глава переводится целиком при загрузке, переводы предложений это не «кэш редких обращений», а нормальные данные главы. Офсеты `start`/`end` те же, что у токенов, — выравнивание с сегментацией бесплатное.
- `glossary_hash` и в `sentences`, и в `lookups`: глоссарий влияет на результат перевода, и после добавления имени героя старые переводы главы устарели. Без этого поля правка словаря будет молча не применяться — и выглядеть это будет как «глоссарий не работает».
- `updated_at` на пользовательских таблицах — под C4. Сервер и так единственный источник истины, но поле стоит копейки и станет нужным в тот день, когда появится оффлайн-клиент.

### 4.4. Тесты и качество

Python 3.12, `ruff`, `pytest`. Отдельно — **золотой набор**: 20–30 предложений на китайском с эталонной сегментацией и ожидаемым переводом. После C3 он нужен раньше и работает на два фронта: показывает, что даёт глоссарий, и станет базой сравнения, если появится второй провайдер.

Для адаптеров сайтов — фикстуры из сохранённого HTML, а не живые запросы в тестах. Для переводчика — записанные ответы; тесты не должны тратить символы.

Фронт (C5): React + TypeScript, Vite. Одна оговорка по рендеру, которая экономит день отладки: глава — это ~3000 токенов-спанов. Не делать компонент на токен с обработчиком на каждом. Один контейнер, один обработчик, делегирование по `data`-атрибутам с офсетами ([segmentation.md](segmentation.md) §4).

### 4.5. Развёртывание и доступ (C2, C4)

Сервер на ВМ — не деталь эксплуатации, а решение, которое добавляет обязательные пункты в MVP.

**Площадка — Yandex Cloud (C2a).** ВМ ещё не поднята: её создание и первое развёртывание входят в MVP, а не предшествуют ему. Это удобно совпадает с C3a — переводчик, объектное хранилище под бэкап и ВМ живут в одном каталоге, под одним платёжным аккаунтом, и настраиваются одним заходом в консоль.

**Состав ВМ:** FastAPI (uvicorn) + SQLite + Playwright/Chromium + reverse proxy (Caddy) с Let's Encrypt. Ориентир по ресурсам: Chromium в пике съедает 1–2 ГБ, так что 2 vCPU / 4 ГБ — разумный минимум, диск от 20 ГБ (словари + FTS5 + Chromium с профилем + кэш глав).

**Авторизация обязательна с первого дня.** Пользователь один (A2), но адрес публичный: за ним чужой контент, словарная выгрузка и платный ключ. Достаточно самого простого — basic auth на уровне reverse proxy или один пароль с сессионной кукой. Чего точно не делать: выкатывать «пока без входа, потом добавлю».

**Ключ Яндекса (C3a)** — сервисный аккаунт в том же каталоге, API-ключ в переменных окружения на сервере. Все вызовы через backend, в React-клиент ключ не попадает никогда. Платёжный аккаунт обязателен: у Translate нет бесплатного объёма.

**Бэкап.** Невосстановим только личный словарь с контекстами. Ночной `sqlite3 .backup` плюс выгрузка в Object Storage того же облака (отдельный сервисный аккаунт с доступом ровно к одному бакету). Снапшот диска не заменяет этого: он не спасает от «случайно удалил строки». Профиль браузера бэкапится вместе с БД — в нём куки Cloudflare. Скачанные главы и переводы формально восстановимы, но перевод стоил денег.

**Синхронизация (C4) получается сама:** сервер — единственный источник истории, позиции чтения и словаря; клиенты тонкие. Отдельного механизма синхронизации и разрешения конфликтов не нужно — он понадобится только вместе с оффлайн-режимом (§3.5).

**SQLite, не Postgres.** Один пользователь, один писатель, никакой конкуренции за запись.

## 5. Предлагаемый порядок работ

Порядок пересобран под A1 и C2. **Честное предупреждение:** MVP дороже, чем в первой редакции, примерно вдвое — в него втянуты браузерный загрузчик, адаптер сайта и минимальная эксплуатация (HTTPS + пароль). Чтобы это не растеклось, MVP урезан до одной главы по прямой ссылке.

**Этап 0 — проверка на выживание, до всего остального.**
Поднять на ВМ Playwright с persistent-профилем и открыть главу `51shucheng.net`. Один день работы, который определяет, остаётся ли план в силе или включается запасной вариант из §6.

**MVP — одна глава китайского сайта, открытая по ссылке.**
URL главы → `BrowserFetcher` → адаптер `51shucheng` → нормализация → сегментация jieba с CC-CEDICT в userdict → **перевод всех предложений главы одним-двумя запросами к Яндексу** → React-ридер → тап по слову → карточка (БКРС + CC-CEDICT + пиньинь + перевод предложения) → сохранение в личный словарь вместе с контекстом. Ручная правка границ выделения. Плюс **экран личного словаря** (M1) и **поднятая ВМ в Yandex Cloud** с HTTPS и паролем (C2a). Всё кэшируется в SQLite.
Не входит: оглавление, «следующая глава», библиотека, английский режим, глоссарий, **ручная вставка текста главы при отказе загрузчика** (M1 — вместо неё внятная причина отказа и повтор).
Объёмы и проверки: [segmentation.md](segmentation.md) §9, [sources.md](sources.md) §4, [translation.md](translation.md) §8.

Обратите внимание: перевод переехал из «этапа 1» в MVP. Раньше он был отдельным этапом, потому что стоил дорого и требовал провайдерского слоя; при посимвольной тарификации и пакетном API это один вызов на главу, и разделять их искусственно нет смысла.

**Этап 1 — глоссарий и качество перевода.**
Проверить поддержку глоссария для `zh→ru`, собирать глоссарий главы из личного словаря по `word_occurrences`, перегенерировать переводы при изменении глоссария, завести золотой набор. Это самый дешёвый доступный рычаг качества на новеллах ([translation.md](translation.md) §4).

**Этап 2 — навигация как в обёртке.**
Оглавление, «следующая глава», позиция чтения, история прочитанного. Только после этого обёртка перестаёт быть демо и становится тем, чем пользуются.

**Этап 3 — подсветка по знанию + статусы слов.**
Раскраска, «знаю/учу/игнор», оценка сложности главы. Дёшево по трудозатратам, осмысленно только на накопленной базе — §3.2.

**Этап 4 — свой ридер.**
Импорт `.txt`/`.epub`, библиотека, экспорт в Markdown/EPUB. Тот же рендер, другой источник — это и есть «фича на после» из ответа A1.

**Этап 5 — английский режим.**
Адаптер `novelarrow`, лемматизация, en→ru словарь.

**Открытый пункт вне очереди — контекстный разбор (недобор по B2).**
Появится, если появится LLM-провайдер: ключ Claude, YandexGPT в том же облаке или что-то ещё. Ставится в план в тот момент, когда решение принято; интерфейс провайдера к нему готов. Варианты — [translation.md](translation.md) §1.

**Позже, вне текущего плана (блок D).**
Повторения (начать с экспорта в Anki — день работы), статистика прогресса, аудио произношения, оффлайн-PWA, параллельный текст. В схеме БД под SRS уже есть `due_at`/`ease`, так что ничего не блокируется.

## 6. Риски

| Риск | Комментарий |
|---|---|
| **Cloudflare + датацентровый IP** | Главный риск, и решение C2 его усилило: челлендж, который домашний браузер проходит незаметно, с адреса ВМ выдаётся жёстче. Проверять **этапом 0**, с самой ВМ, а не с ноутбука. Лестница отступления: (1) headful через Xvfb с persistent-профилем; (2) выпускать трафик ВМ через домашний адрес (WireGuard или прокси на домашнем роутере), сохраняя весь сервис на ВМ; (3) гибрид — загрузчик крутится на ноутбуке и отдаёт текст в API, ВМ держит БД и словари; (4) расширение в браузере, скачивание целиком на стороне пользователя. Варианты 3 и 4 сохраняют всю остальную работу, но меняют схему развёртывания — лучше узнать об этом в первый день. **Перенос профиля с ноутбука на ВМ ступенью не является:** `cf_clearance` привязан к IP и обычно к User-Agent, так что скопированные куки на другом адресе почти наверняка не сработают. |
| **Качество машинного перевода на новеллах** | Новый риск от C3, и он ощутимее ценового. Имена собственные, культивационная терминология, чэнъюй, 离合词 — то, на чём MT предсказуемо ошибается, и именно этого много в веб-новеллах. Меры: глоссарий из личного словаря (этап 1), золотой набор для замера, готовность при провале взять текст попроще. Проверять на реальной главе до того, как строить планы. |
| **Контекстный разбор недоступен (недобор по B2)** | Машинный переводчик не объясняет, почему здесь такое значение. Для начального уровня терпимо, дальше начнёт мешать. Отслеживать по себе: как только «перевод есть, а понимания нет» станет регулярным — вернуться к вопросу об LLM-провайдере ([translation.md](translation.md) §1). |
| **Публичный сервер** | Адрес в сети + чужой контент + платный ключ. Без HTTPS и пароля инстанс — это раздача чужих текстов и чужой счёт. §4.5, не откладывать. |
| **Художка при начальном уровне** | A4 + B6 — самая тяжёлая комбинация: 40–60% незнакомых слов, вымышленные имена, литературный синтаксис. Меры: перевод предложения уже в MVP, параллельный текст как запасной режим. |
| **Хрупкость адаптеров** | Обёртка живёт на чужой вёрстке: смена DOM или маршрутов ломает импорт. Меры: тесты на сохранённых HTML-фикстурах, generic-фолбэк, внятная диагностика вместо пустой главы. |
| Качество сегментации | jieba ошибается на именах собственных и литературном языке — для новелл это норма. Ручная корректировка с первого дня: [segmentation.md](segmentation.md) §2, §4, §5. Теперь она же кормит глоссарий. |
| zh→ru словарь | Решается выгрузкой БКРС (B3), но формат дампа и качество импорта надо проверить на реальных статьях. После C3 словарь — единственный источник значений, так что его качество стало критичнее. |
| Стоимость перевода | Низкая и предсказуемая: ~2,5 ₽ за главу, ~250 ₽ за сотню. Логировать отправленные символы всё равно — [translation.md](translation.md) §7. |
| Потеря данных | Личный словарь с контекстами невосстановим, переводы оплачены. Бэкап SQLite за пределы ВМ — §4.5. |
| Разрастание скоупа | Держать границу «одна глава по ссылке» жёстко. |

### D. Обучение — отложено за пределы MVP

Решения принимаются после MVP; ничего в схеме данных они не блокируют.

1. Повторения (SRS) или экспорт в Anki? — поля `due_at`/`ease` заложены, экспорт `genanki` стоит день работы.
2. Статистика и прогресс — бесплатное следствие `word_occurrences` и статусов слов (этап 3).
3. Аудио произношения — единственный пункт, требующий отдельной работы. С учётом начального уровня (B6) может оказаться нужнее, чем кажется.

## 8. Короткая версия

- Обёртка идёт первой (A1) — это **меняет порядок работ, а не архитектуру**: живой сайт и импортированный файл различаются одним слоем.
- Расплата — **более дорогой MVP**: браузерный загрузчик, адаптер сайта и минимальная эксплуатация втянуты в первый этап. Граница: одна глава по прямой ссылке.
- **Оба целевых сайта требуют реального браузера** ([sources.md](sources.md)), а C2 сажает этот браузер на датацентровый IP. Проверить проходимость Cloudflare с ВМ — **этап 0**.
- **Сервер — не только удобство:** HTTPS, пароль и бэкап входят в MVP.
- **Яндекс.Переводчик (C3) закрывает главную потребность и удешевляет её**: посимвольная тарификация делает перевод всей главы при загрузке (~2,5 ₽) выгоднее перевода по требованию. Чтение идёт без сети и без задержек.
- **Но контекстного разбора не будет** — половина B2 остаётся незакрытой осознанно. Провайдер за интерфейсом, добавление LLM позже стоит один файл ([translation.md](translation.md) §1).
- **Глоссарий из личного словаря** — главный рычаг качества на новеллах, и он же превращает правку границ сегментации в улучшение перевода.
- Словарь: БКРС основной (B3) и теперь единственный источник значений; CC-CEDICT для пиньиня и сегментации.
- Сегментация — фундамент; для новелл правка границ обязательна с первого дня ([segmentation.md](segmentation.md)).
- Подсветка по знанию — после накопления базы; в MVP заложить только `status` и `word_occurrences`.
