# Сегментация китайского текста: как реализовать

Ответ на вопрос «как это реализовать» из [concept-review.md](concept-review.md) §3.

Задача: пользователь читает `我喜欢学习中文`, тыкает в `习` и должен получить карточку слова `学习`, а не символа `习` и не всей строки. При этом сегментатор регулярно ошибается, и пользователь должен иметь возможность поправить границы руками.

## Общая схема

```
загрузка главы (живой сайт → кэш; после этапа 5 — ещё и импорт файла)
  └─ нормализация (полноширинная пунктуация, zero-width, пробелы)
  └─ сегментация → список токенов с офсетами
  └─ сохранение: оригинальный текст + tokens_json (текст не портим)

рендер главы
  └─ span на токен, data-атрибуты с офсетами

клик по токену
  └─ lookup_key → личный словарь → CC-CEDICT → (пост-MVP) API
  └─ карточка

правка границ пользователем
  └─ новое слово → user_words → userdict сегментатора
  └─ следующие тексты режутся правильно
```

Сегментация делается **один раз, при загрузке главы** (и результат кэшируется вместе с текстом), а не на лету при рендере. Иначе: тормоза на каждой прокрутке, и — что хуже — рассинхрон между тем, что показано, и тем, что сохранено в словарь.

## 1. Токен = офсеты, а не строка

```python
@dataclass(frozen=True)
class Token:
    start: int          # индекс символа в тексте главы
    end: int
    surface: str        # как в тексте: 学習 / 学习 / OK / 1998
    kind: TokenKind     # word | punct | latin | digit | space
    lookup_key: str     # ключ для словаря (упрощённое, нижний регистр)
```

Почему офсеты, а не просто список строк:

- текст главы остаётся нетронутым в БД — можно переразметить его другим сегментатором, не трогая контент. Уточнение, чтобы не было расхождения с §7: **каноном считается нормализованный текст**, а не то, что пришло с сайта. Нормализация происходит один раз, до сегментации; офсеты токенов и границы предложений считаются по канону; сырой HTML не хранится;
- контекст-предложение для карточки вырезается из оригинала по офсетам;
- правки границ — это правка разметки, а не текста.

`jieba.tokenize(text)` возвращает кортежи `(word, start, end)` — ровно то, что нужно, конвертация в `Token` тривиальна.

## 2. Согласовать сегментатор со словарём — самое важное

По умолчанию jieba режет по **своему** словарю, который не совпадает с CC-CEDICT. Из этого два перекоса:

- jieba склеил то, чего нет в словаре → клик по слову даёт «не найдено»;
- jieba разрезал то, что в словаре есть единой статьёй → пользователь видит два бессмысленных куска.

Лечится загрузкой словаря приложения в jieba:

```python
# lang/zh/segmenter.py
import jieba

def build_userdict(cedict_entries, user_words) -> None:
    for e in cedict_entries:
        jieba.add_word(e.headword, freq=estimate_freq(e))
    for w in user_words:                    # слова, добавленные пользователем
        jieba.add_word(w.headword, freq=HIGH)
```

Это одна из самых дешёвых мер с самым большим эффектом: сегментация и словарь начинают говорить об одном и том же.

Про `freq`: jieba выбирает разбиение по максимуму произведения частот, поэтому частота — не украшение, а рычаг. Без явной частоты jieba проставит эвристическую, и длинные редкие слова из CC-CEDICT начнут выигрывать у коротких употребимых. Практично: взять частоту из штатного `dict.txt` jieba, если слово там есть; для остальных — низкую базовую; для слов пользователя — заведомо высокую (он их явно выделил, значит хочет видеть их целиком). Пост-MVP: подложить нормальный частотный список (SUBTLEX-CH, BCC).

## 3. Выбор сегментатора

| Библиотека | Качество | Скорость / вес | Комментарий |
|---|---|---|---|
| **jieba** | среднее | очень быстрый, лёгкий | расширяется словарём, HMM для новых слов. **Выбор для MVP** |
| **pkuseg** | выше | медленнее, модель ~100 МБ | доменные модели (news / web / tourism / medicine) — заметно лучше на художке |
| **HanLP / LTP** | лучшее | тяжёлые, нужен torch | оправданы, только если качество упрётся |
| **Intl.Segmenter** | среднее | встроен в браузер/Node | ICU, ноль зависимостей — вариант, если фронт сегментирует сам |

Прятать за интерфейсом с самого начала:

```python
class Segmenter(Protocol):
    def segment(self, text: str) -> list[Token]: ...
```

Смена сегментатора не должна стоить дороже одного файла. И сразу завести **золотой набор**: 20–30 предложений с эталонной разметкой, чтобы смена/донастройка измерялась, а не оценивалась на глаз.

## 4. Правка границ пользователем

Даже с настроенным словарём сегментатор ошибается — на именах собственных, редкой лексике, литературном языке. Для художественной литературы это не край, а норма: вымышленные имена из новелл jieba не знает в принципе.

Взаимодействие:

| Действие | Результат |
|---|---|
| клик / тап по символу | выделяется его токен целиком (`学习`) |
| drag или shift-клик по соседнему | выделение расширяется по границам токенов → фраза |
| долгий тап / alt-клик | сузить до одного символа (`习`) |

Два ограничения, без которых получается мусор:

- расширение **не пересекает границу предложения** (`。！？；`, перевод строки) — иначе легко собрать бессвязный кусок;
- при сужении до символа span активного токена динамически разбивается на символы, остальной текст остаётся отрендеренным по токенам.

Рендер: `<span data-s="12" data-e="14">学习</span>` на токен. Для главы в 5000 иероглифов это ~3000 узлов — DOM это переживает. Для книги целиком — виртуализация по абзацам, но это уже вопрос рендера, а не сегментации.

## 5. Правки должны учить систему

Когда пользователь склеил `江雪明` в одно слово и сохранил его — записываем это в `user_words` и подкладываем в userdict. Дальше:

- все последующие главы режутся правильно;
- по конкретной главе, где ошибка уже видна, можно применить `segmentation_overrides` и переразметить её на месте.

В новеллах имя героя встречается сотни раз — одна правка окупается мгновенно. Это самоулучшающаяся часть системы и стоит она почти ничего.

## 6. Что хранить в БД

Два варианта:

- **A. `chapters.tokens_json`** — массив `[start, end, kind]`. Просто, читается одним запросом, это ровно то, что нужно фронту для рендера.
- **B. таблица `tokens`** — позволяет спрашивать «где ещё встречалось это слово», но книга даёт сотни тысяч строк.

Рекомендация — A для рендера плюс агрегат для поиска:

```sql
word_occurrences (headword, chapter_id, count)
```

Этого хватает и для статистики, и для «покажи другие примеры этого слова», без раздувания.

## 7. Нюансы, которые всплывут

**Традиционные иероглифы.** jieba обучен на упрощённых и на традиционном тексте режет заметно хуже. Схема: сконвертировать текст в упрощённый через `opencc` **только для сегментации и поиска в словаре**, а показывать оригинал. Отсюда и разделение `surface` (оригинал) / `lookup_key` (упрощённое) в §1.

**Смешанный текст.** Латиница, цифры, пунктуация в китайском тексте — обычное дело. `kind` нужен, чтобы фронт не делал кликабельными запятые, а латинские слова уводил в английский словарь, а не в китайский.

**Нормализация на входе.** Полноширинная пунктуация (`，。！`), неразрывные и zero-width пробелы, разные виды кавычек — привести к канону до сегментации, иначе офсеты и словарные ключи разъедутся.

**离合词 и результативные конструкции.** `帮忙` → `帮了忙`, `看得见` — generic-сегментация их разрывает. Для MVP игнорируем; лечится словарём паттернов, но это отдельная задача.

## 8. Английский — та же задача, другая механика

Сегментация тривиальна (пробелы), но нужны:

- **лемматизация**: `running / ran / runs → run`, иначе личный словарь заполнится дублями одного слова. `spaCy` или `lemminflect`;
- **многословные выражения**: `give up`, `look forward to` — токенизацией не ловятся, только словарём фраз с поиском по n-граммам.

То есть общий интерфейс `Segmenter` покрывает оба языка, а внутри — разные реализации.

## 9. Объём для MVP

Источник текста в MVP — глава, загруженная с сайта ([sources.md](sources.md)), а не файл: на сегментацию это не влияет никак, кроме того, что нормализация входа (§7) становится обязательной — HTML-извлечение приносит больше мусора, чем чистый `.txt`.

Входит:

- jieba + CC-CEDICT в userdict;
- токены с офсетами в `tokens_json`, нормализация входа;
- клик = токен, drag = склейка в пределах предложения, долгий тап = символ;
- слова пользователя → userdict.

Не входит:

- pkuseg и доменные модели;
- `segmentation_overrides` по главам;
- нормальные частотные списки;
- 离合词 и прочая грамматическая машинерия.
